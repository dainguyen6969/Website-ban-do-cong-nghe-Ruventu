# Warranty frontend transport check

Contract source: user-supplied `Thiết_kế_API.xlsx`, sheet `Tổng hợp toàn bộ API`, BH01–BH014, compared with the existing Java controller, request DTOs and validators. Handover is now sourced from main-test `1bd51cd`: `WarrantyHandoverValidation`, `WarrantyHandoverChecks` and `WarrantyHandoverTransactions`. No backend or API contract is changed. Original fixtures contain sample data from that workbook; the added paginated history and handover responses are synthetic transport cases.

Run from repository root with the installed Postman CLI:

```powershell
postman simulation run FRONTEND/tests/warranty-api/warranty.sim.yaml --port 4900 --output ndjson --no-history
```

In a second terminal, from `FRONTEND`:

```powershell
node --test src/features/admin/warranty/data/warrantyContract.test.js
node --test tests/warranty-api/transport.test.js
```

Optional browser check, from `FRONTEND`:

```powershell
$env:VITE_RUVENTU_API_URL='http://127.0.0.1:4900/warranty'
node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5174
```

Open `http://127.0.0.1:5174/tests/warranty-api-preview.html`. This isolated test origin uses a dummy token. Do not use that page as the normal authenticated admin entry point.

The simulation exercises the production HTTP client: list, lookup, detail, twelve mutation routes including handover, history pagination beyond 100 entries, same-key replay, changed-body conflict, 400, 409, 404 and 503. Handover checks include structured outstanding-payment data, completion followed by replay and rejecting a second completion. The sentinel debt ID 999999 injects a payment refusal only in this mock; it does not simulate actual financial authorization. Pure checks cover exact handover fields, recipient validation, explicit acknowledgment, evidence and original/replacement identity.

Limits: the mock keeps local state only until restart and implements only frontend transport behavior. Responses for most operations are workbook snapshots. It does not prove backend authorization, inventory/accounting, all business transitions, upload storage, or database correctness. No real financial transaction is executed. Unmodeled routes return 501. Handover business rules are tested separately in the Java suite and on the live BH-000008 sample; PC-component intake remains outside this work.

2026-10-31 live evidence: BH-000008 reached HOAN_TAT with one HANDOVER event, no invoice or money transaction. Missing acknowledgment, wrong device/accessories and new-key duplicate attempts were rejected. Browser review on BH-000011 exercised required acknowledgment and the confirmation dialog without saving that ticket. Its draft test values were discarded by navigation.
